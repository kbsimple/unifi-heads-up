## Summary

Four files implement a rolling-average traffic-status classifier: `db/index.ts` exposes `getRecentAvgRates` (CTE window query), `recorder.ts` orchestrates polling and smoothing, and two test files exercise both modules. The overall approach is sound — parameterised statements prevent SQL injection, the CTE window logic is correct, and the fallback for new clients (pass-through of instant status) is explicit and tested.

Three warnings require attention before relying on this in production: a missing composite index makes the window query table-scan-heavy on large snapshot sets; `upsertLatestClients` silently swallows an empty-array call and could leave the cache stale without any signal; and `recorder.ts`'s module-level `started` flag is never reset, making test isolation dependent entirely on `vi.resetModules()` (which the test suite does do correctly, but it is a fragile coupling). Two info items cover minor quality gaps.

## Warnings

### WR-01: Missing composite index on `(client_mac, recorded_at)` causes full-table scan in window query

**File:** `src/lib/db/index.ts:28`

**Issue:** The only index on `snapshots` is `idx_recorded_at` on the single column `recorded_at`. The CTE in `getRecentAvgRates` filters `WHERE client_mac IN (...)` and orders `BY recorded_at DESC`. SQLite cannot use a single-column `recorded_at` index to satisfy both the `IN` predicate and the ordering at the same time; it falls back to a full-table scan + sort. With SNAPSHOT_WINDOW=2 and a 30-day retention window at 60-second polling, the table can accumulate ~43,000 rows per client. The existing index therefore gives no benefit to the hot query path.

**Fix:** Replace (or augment) the index with a composite covering index:

```sql
CREATE INDEX IF NOT EXISTS idx_snapshots_mac_at
  ON snapshots (client_mac, recorded_at DESC);
```

Drop `idx_recorded_at` if it is not used elsewhere, or keep both. The composite index lets SQLite seek directly to each MAC's most-recent rows, making the window query O(W) per client instead of O(N).

### WR-02: `upsertLatestClients` returns silently on empty array — stale cache is invisible to caller

**File:** `src/lib/db/index.ts:85-86`

**Issue:** When `clients.length === 0` the function returns immediately without touching the database. If the UniFi API briefly returns an empty client list (e.g., a transient poll glitch), the `latest_clients` table retains its previous contents indefinitely with no indication that the data is stale. `getLatestClients` will continue serving the old rows as long as `updated_at` is within `maxAgeMs`, making it impossible to detect the silent drop.

This is a correctness concern: the caller in `recorder.ts` (line 33) passes `smoothed` which was derived from the just-fetched client list. If `getUnifiClients` returned zero clients legitimately, the recorder silently keeps old cached data live rather than marking it stale or clearing it.

**Fix:** Either (a) allow `upsertLatestClients([])` to proceed normally — the `DELETE FROM latest_clients` runs, clearing the cache so `getLatestClients` will return `null` on the next dashboard request — or (b) make the early-return explicit by logging a warning so operators know when a zero-client poll occurs:

```typescript
export function upsertLatestClients(clients: NetworkClient[]): void {
  const database = getDb()
  const now = Date.now()

  const upsertAll = database.transaction((rows: NetworkClient[]) => {
    database.prepare('DELETE FROM latest_clients').run()
    if (rows.length === 0) return   // cache cleared; getLatestClients returns null

    const insert = database.prepare(`
      INSERT INTO latest_clients (
        id, mac, display_name, ip, last_seen, is_wired, is_guest,
        download_rate, upload_rate, signal, traffic_status, updated_at
      ) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)
    `)
    for (const client of rows) {
      // ... existing run() call
    }
  })

  upsertAll(clients)
}
```

Alternatively, keep the guard but add a `console.warn('[recorder] upsertLatestClients called with empty list — cache unchanged'` so the silent drop becomes observable.

### WR-03: `started` flag in `recorder.ts` is module-level state that leaks across re-imports unless `vi.resetModules()` is called

**File:** `src/lib/db/recorder.ts:12-13`

**Issue:** `let started = false` is module-level. Because `vi.resetModules()` is called in `beforeEach`, the recorder test suite currently works correctly — each test gets a fresh module with `started = false`. However, this is an implicit coupling: if any future test imports `recorder` without resetting modules (e.g., in an integration test or a test helper), the `started` flag from a previous test will persist, causing the interval to never register and the test to silently pass vacuously.

The idempotency guard itself is correct and necessary. The fragility is that there is no exported reset mechanism and the module has no documented lifecycle contract.

**Fix:** Export a `resetRecorder()` for test environments, or convert the guard to accept an injected flag so it is not module-global:

```typescript
// For test environments only
export function _resetForTests(): void {
  started = false
}
```

Then each `afterEach` in the test file can call `_resetForTests()` explicitly, removing the implicit dependence on module re-import order.

## Info

### IN-01: `getRecentAvgRates` passes `window` as the last positional parameter but `macs` count varies — ordering of `all([...macs, window])` is correct but fragile to future edits

**File:** `src/lib/db/index.ts:210`

**Issue:** The SQL string embeds `${placeholders}` for the MAC list and then appends a single `?` for the `window` parameter (line 208 `WHERE rn <= ?`). The call `.all([...macs, window])` relies on the spread ordering being exactly right. This is not a current bug — the code is correct — but the positional binding makes it easy to accidentally misorder parameters if the query is extended (e.g., adding a date-range filter before the `window` filter).

**Fix:** No code change required. Consider a comment noting the parameter ordering contract:

```typescript
// Parameters: ...macs (N values for IN clause), then window (1 value for rn <= ?)
.all([...macs, window])
```

### IN-02: `recorder.test.ts` test "calling startRecorder twice" relies on `vi.resetModules()` in `beforeEach` but imports modules inside the test body — import order is sensitive

**File:** `tests/lib/db/recorder.test.ts:92-104`

**Issue:** The idempotency test (line 92) imports `startRecorder` after the mocks are already wired up via the top-level `vi.mock(...)` hoisting. This works because `vi.resetModules()` in `beforeEach` flushes the module registry, causing the subsequent dynamic `await import(...)` calls inside each test to pick up fresh module instances with mocks applied. The pattern is correct but non-obvious. If a developer adds a static import at the top of the test file, it will bypass the reset and re-introduce stale state.

**Fix:** Add a comment at the top of the describe block explaining the pattern:

```typescript
// All imports are dynamic (inside each test) because vi.resetModules() in beforeEach
// resets the module registry. Static top-level imports would bypass this and retain
// the `started = false` state from module initialisation.
```
